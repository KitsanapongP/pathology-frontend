## Project instructions

- UI: don't add taglines, eyebrow labels, decorative subtitles or helper text by default. If a screen only makes sense with them, fix the layout instead. Keep text that carries information the layout can't: errors, units, consequences of destructive actions, accessibility labels.
- In code you write or change, keep it agent-friendly: scripts run non-interactively, errors say what to do next, and the project's AGENTS.md is updated when a non-obvious convention is set.

# Repository conventions

## Local infrastructure and test setup

- `docs/development-setup.md` describes Docker, GitLab CI, security limits and the pending real Postman contract. Publication must follow the user's requested remote and scope; authorization to push GitHub does not authorize uploading the initial frontend to GitLab.
- `npm test` runs Node examination tests and Vitest. Vitest includes only `tests/unit/**/*.test.{ts,tsx}`; Playwright includes only `tests/e2e`. Keep these runners separate. Node runtime and `@types/node` target version 24.
- `npm run check` is non-interactive lint, typecheck, unit tests and build. `npm run test:e2e` builds and starts a fresh production server on loopback port 3100; never reuse the user's browser/session or existing server for these isolated tests.
- Playwright browser binaries are separate per-user downloads. For a missing executable, use `npx --no-install playwright install chromium` in the test user's environment; use `--force` only if that download is damaged. Keep setup/troubleshooting in `docs/development-setup.md`.
- Docker alone sets `DOCKER_BUILD=true` for standalone output. Keep normal local builds and GitHub Pages export behavior. Runtime uses a non-root user and Compose publishes only on loopback. Never copy `.env` or private keys into the image.
- GitLab configuration runs validation/audit/browser tests only, with no deploy. GitLab Runner/CI Lint verification requires the maintainer and has not been performed just by adding the YAML. Only the documented health endpoints are in the Postman collection; business/auth requests require the actual OpenAPI contract. Never commit real responses/tokens or the private dev IP environment (`postman/dev.local.json`).
- After adding dependencies, verify `npm ci` on both Windows and Linux. npm has omitted optional native dependency entries when generating the lockfile against an existing Windows `node_modules`; regenerate the lockfile in a clean Linux container if Linux `npm ci` reports missing `@emnapi` entries. Do not replace CI's `npm ci` with `npm install` to hide the mismatch.



## Examination workstation

- `/portal/examinations` uses **explicit, bounded foot targets**, not generic DOM scanning. The active root is the bottom command rail or the topmost native dialog. `use-examination-focus.ts` only accepts `[data-pedal-target]`; never restore button/input/link selectors or add the report/header to the foot cycle.
- Recording has four normal rail targets: current Part, complete Part, review/send, tools. Latest-line editing lives in Tools. Autosave replaces the normal save button; a failed save exposes an explicit retry target. Review provides current Part, editing, confirmation and tools; confirmed reports remain visible with a next-case action. The report, Part status strip, header, notices and developer tools are not foot targets. Add a primary action to the rail; put secondary actions in the tools dialog.
- Standby and case share the same persistent lookup section: input, small example, top-down pedal graphic and speech cue stay visible after finding a request. Case displays its details alongside lookup; do not restore the duplicate case bar there. Accession belongs in the case card. Case center hold uses search speech (and still accepts existing navigation commands); users can replace a request without backing out. The case rail offers search and start/open, not a required back step. Keep selected request identity in the patient context card on record/review.
- Case readiness lives directly beneath the search input. `recordingBlockReason` and `readyForRecording` share one gate: completed OCR, approved request data (`พร้อมใช้งาน`), and accession. Green means entry is available; red explains the blocker. A saved draft does not grant entry. Never restore the generic “มีงานที่บันทึกไว้ ทำต่อได้” toast. A failed draft read also blocks entry and labels the retry action explicitly.
- Each chooser is a separate `ExaminationPanel` context with an explicit target list: tools, results, line picker, buffered entry/edit, or playback. Mark the initial choice `data-pedal-default`. Header X buttons can remain mouse controls because left double-tap closes every dialog. The help dialog explicitly marks its close and scroll actions.
- Left/right tap cycles only the active target set. Center tap activates; center hold after 250ms opens push-to-talk; release stops capture. Left double-tap backs/closes; right taps always advance immediately; help lives in Tools on record/review and directly on the standby/case rail (left double-tap window: 350ms). Part completion and final confirmation each use a fresh 3-second right hold and release on their explicit target; neither opens the microphone. Direct pointer/Enter/Space hold buttons supply their own binding and progress bar.
- Main rails with multiple actions show non-interactive left/right pedal cues and outward arrows flanking the action row. Center activation is centered above that row. Only the back shortcut remains below, hidden during Part adjustment; a single-action rail needs no directional cues. Modal gesture strips retain their navigation instruction. Do not repeat pedal instructions under every action or inside the report. All instructional text uses `--hint` (18px). Sample-data hints also use the same 18px scale, kept as a single plain line; content/report text is 22px and headings may be larger. Do not add sample-data buttons.
- `ExaminationFootKey` shows only the three-pedal pictogram with one physical position highlighted. Do not add visible ซ้าย/กลาง/ขวา captions. Its `role=img` and `aria-label` retain the position for assistive technology. The main activation cue says เลือก; arrows and action icons convey navigation/function.
- Record center hold normally dictates into the current Part. Tools → พูดคำสั่ง arms one command capture only; it never opens the microphone automatically and must return to dictation after capture/cancellation. Show the armed destination explicitly. Do not restore a persistent mode picker or the microphone header box. Search and edit fields retain contextual speech. Non-text choosers and active Part adjustment do not open the mic.
- The current-Part rail button uses `data-pedal-adjust="part"`: center enters inline adjustment, both sides change the actual report Part immediately even when tapped rapidly, and center exits adjustment. Keep the same bounded target selected, show that the rail is adjusting Part, and cancel adjustment when opening another context. Do not open a Part picker for this main action.
- Returning from a chooser or nested help restores its invoking target when available; entering a new main step uses its default. Restoration remains bounded to the active root and falls back if the old target is unavailable. Range controls may specify `data-pedal-step` separately from native `step`: playback uses five-second pedal seeks while pointer input retains finer precision.
- Review presents all enabled or populated Parts together, including explicit empty sections for added Parts; emptiness is not a validation failure or proof a Part has been reviewed. Confirmation must show case identity and explain local locking before the hold gesture; it is not hospital submission. Keep report content out of the pedal target cycle.
- The record rail offers แก้ล่าสุด through the existing buffered editor. Cancel returns to the opener and never commits. Highlight newly appended lines briefly; auto-follow only if the reader was already near the report bottom before the append.
- Notices carry explicit error/success/info tones. Render feedback only in the topmost active dialog, or on the main screen if no dialog is open. Success/info expires; errors persist. Modal retry actions are an explicit exception to the non-target notice rule; they join only that dialog's bounded targets. Main-screen retries use existing rail actions, never add page-wide targets. Save completion feedback must match the current request and snapshot revision, and explicit save cancels a pending autosave timer.
- Entry and line editing use a local text buffer in a modal. `[data-pedal-field=entry|line]` routes speech into that buffer. Only the modal save/add action changes the report; backing out discards the buffer. Undo/redo operates on committed report snapshots.
- `examination-controls.ts` defines hardware F13/F14/F15, test aliases F8/F9/F10, timing and gesture contexts. Hardware, keyboard aliases and pointer simulator share the controller. Capture origin/binding at press time, reject stale-context actions and cancel gestures/voice on context changes, blur and unmount. Preserve topmost-dialog isolation and pointer click-through protection.
- `examination-speech-preview.ts` is a removable Thai browser STT adapter, not production STT. Never add a latched microphone toggle, including developer tools. A released permission request must not start recording later. Service support detection is not proof of audio accuracy.
- `ExaminationMicStatus` shows only the lamp, with a screen-reader-only state label. Do not restore the header status box or visible mic captions. Place it inside the search field beside submit on standby/case, beside report metadata on record/review, or in the active dialog; render only one active indicator and keep the search slot's width stable while a dialog is open. Gray means off; amber means starting or processing; the red glowing lamp means capture. Recognition-only modes wait for `onaudiostart` before reporting capture, and use `onaudioend` for processing. Dictation reflects the MediaRecorder capture lifecycle. Late capture callbacks must check the active session and cancellation.
- The development-only simulator has three physical buttons. Command injection is collapsed by default and excluded from foot selection. Render exactly one simulator in the active modal or main shell; preserve its open state across contexts. Both its toggle and panel are fixed overlays: never reserve shell padding or change dialog widths/margins when it opens.
- Request records are fixtures; text/audio persist in this browser's IndexedDB. Local confirmation is not hospital submission or a clinical signature. Preserve unrelated data and do not finalize an existing draft merely for QA.
- Update `docs/examinations-interaction-spec.md` with every mapping/layout change. Keep current browser checks and honest hardware/STT limits in `docs/examinations-qa.md`. Check both 1896×1244 with the simulator and 1280×720; tests alone do not prove visual quality.

## Shared API transport

- Temporary skip-login shortcuts are explicitly enabled with `NEXT_PUBLIC_AUTH_MODE=demo` in local preview/Compose/GitHub Pages while backend accounts are unavailable. Keep the real username/password form primary; shortcuts are small bottom-right actions outside the card (flow below it on mobile to avoid overlap). Choosing a shortcut clears the local real session and uses only `pathology:demo-session:v1`, creates no auth tokens and blocks service HTTP calls while previewing. Real login remains usable before choosing a shortcut; real authenticated/password-required states keep API guards. `api` (or unset) hides shortcuts. Never add fake tokens or weaken mandatory-password guards. Use `npm run test:e2e:demo` separately; normal E2E forces API mode.

- All pathology-portal-service HTTP calls must use `src/lib/portal-api.ts` in browser code, or a request-scoped `createApiClient` from `src/lib/api-client.ts` on the server. Do not add direct fetch/axios calls in pages or feature adapters. Existing fixtures stay local until real endpoint contracts are supplied.
- Set `NEXT_PUBLIC_API_BASE_URL` before building; local portal is `http://localhost:9100`, dev uses `http://<DEV_IP>:9100` (no domain yet, same network/VPN), and prod is `http://portal.<domain>` with the domain pending. Keep the real private dev IP in ignored local env files. The client owns `/v1`. Request service is separate on port 8000; do not route its future business calls through portal. Auth hands token sets to `portalSession.accept`; access tokens stay in memory and refresh tokens use `pathology:session:v1` sessionStorage (agreed with the user). Never persist tokens in portal preferences. Only public endpoints explicitly use `auth: false`. See `docs/session.md` for refresh/guard/race conventions and the backend's lack of access-token revocation.
- Login uses Swagger's maximum lengths (username 100, password 256); password change requires at least 8 characters. Count Unicode code points in submit validation to match JSON Schema character lengths rather than JavaScript UTF-16 units. User-list queries use `page` and `size`; only the response pagination field is named `page_size`.
- Branch on `ApiError.errorCode`, never `message`. Render backend messages as text without translating again. Use `ApiFieldErrors` with `aria-invalid`/`aria-describedby` for canonical backend field names, and `ApiErrorNotice` for general feedback, 5xx request IDs and 429 guidance. See `docs/api-client.md` for usage and the pending backend CORS handoff.
- A `must_change_password` session can render only `/change-password`; refreshing never clears that gate. Password-change success clears the whole local session and places only a one-time success code in `pathology:login-notice:v1` for the login page. Never persist password form values or auto-login after a password change.

## Part completion and capture feedback

- The recording heading has no visible title, logo, saved label or line count. A large right-facing speaker turns green only on MediaRecorder.onstart; an AnalyserNode draws signed time-domain input as a full-width smoothed continuous waveform (silence stays flat, never fabricate waves). The timer includes accumulated clips and live capture. Search/dialog indicators retain their compact lamp. No monitoring audio is routed to speakers.
- New cases expose A only. Persist optional completedPartIds on v2 drafts; unlock/advance to the next Part only after a successful 3-second completion save. Empty next Parts are optional and omitted from review/confirmation. Parts with legacy text/audio remain visible. Remove manual add-Part shortcuts. Editing/undo/redo or appending audio invalidates completion of the changed Part; all populated Parts must be completed before final confirmation. Never lock the report when merely completing a Part.
- The 3-second hold is evaluated on release; short right release navigates normally without saving; cancellation or stale request/Part/context must not save or finalize. Save failures stay on the same Part and expose retry. Local final confirmation remains a local lock, not hospital submission.

- Center hold always retains contextual push-to-talk, including when completion/confirmation is selected. Right hold saves only on the selected completion/confirmation target; right tap still navigates. Keep the target binding captured on press, and update every cue/progress bar to the right pedal.
- Small pedal pictograms preserve the original geometry and gray inactive keys. Only the indicated key is colored using pedalBindings.highlightColor: left orange, center blue, right purple. Do not tint all three keys, enlarge the indicated key or recolor the hardware illustration/simulator surfaces. The hardware drawing's thin accent strips and active outline use the same highlightColor as the small pictograms. Preserve the existing role/position aria-label and no visible captions.

- PortalFrame normalizes trailing slashes before matching the examination route. GitHub Pages exports use trailingSlash:true, so both /portal/examinations and /portal/examinations/ must hide the header and receive portal-frame--station. Do not match unrelated route prefixes.
